\chapter{Réalisation}

Ce chapitre décrit l'implémentation \textbf{effective} : organisation du code, choix techniques, points d'implémentation notables et écrans illustrés par les captures intégrées.

\textbf{Lecture de la stack.} Le terme \textbf{MERN} désigne ici l'association MongoDB, Express.js, React et Node.js. Next.js est le framework utilisé autour de l'application React web ; TypeScript apporte un typage statique aux clients web et mobile. Express.js expose l'API REST du backend Node.js, avec des échanges JSON, tandis que MongoDB assure la persistance des utilisateurs, agents, conversations et messages. Mongoose définit les schémas utilisés par le backend.

\textbf{Client mobile.} React Native et Expo constituent une application séparée du frontend Web, partageant le backend REST et Socket.io. Cette stack mobile n'est donc pas une composante supplémentaire de MERN.

\textbf{IA et recherche documentaire.} Le service Google Gemini génère les réponses lorsqu'il est disponible. Avant cette génération, le retriever local normalise les textes, calcule des scores TF-IDF et compare les vecteurs par similarité cosinus afin de sélectionner les éléments pertinents de la base de connaissances. En l'absence de réponse Gemini exploitable, le backend dispose également d'un repli local.

\textbf{Temps réel et authentification.} Socket.io complète l'API REST pour diffuser les messages et les mises à jour de conversations. Google OAuth intervient dans l'identification client, tandis que des jetons JWT représentent les sessions client, agent et administrateur et sont contrôlés par les middleware du backend.

\textbf{Tests et variantes MongoDB.} Jest orchestre les tests, Supertest vérifie les routes HTTP et MongoDB Memory Server fournit une base isolée pour les tests automatisés. \textbf{MongoDB} désigne la technologie de persistance ; \textbf{MongoDB Atlas} désigne le service distant documenté pour l'environnement de production ; \textbf{MongoDB Memory Server} est réservé à l'isolation des tests. Git et GitHub assurent le versionnement et l'hébergement du dépôt. Postman est mentionné dans la documentation du projet pour les vérifications manuelles de l'API ; aucun compte rendu détaillé ni collection Postman n'est conservé dans le dépôt.

\textbf{Justification succincte.} Next.js fournit le routage et un frontend React moderne, conformément à l'orientation \og React \fg{} du sujet. Express est l'API demandée côté Node. MongoDB Atlas évite d'administrer un serveur local de production. Gemini a été retenu (et utilisé effectivement) plutôt qu'OpenAI. Socket.io couvre le besoin de réactivité du chat et de la file agent. JWT sépare clairement sessions client et sessions agent.

\subsection{Déploiement et hébergement}

La chaîne de déploiement vérifiée est \textbf{GitHub $\rightarrow$ Vercel (Web)} et \textbf{GitHub $\rightarrow$ Render (Backend)}. Le frontend public est accessible à \texttt{https://sinaps-pfa.vercel.app} et utilise l'API Render \texttt{https://sinaps-backend-jm1h.onrender.com/api}. L'endpoint \texttt{GET /api/health} a répondu avec le statut HTTP 200, puis une identification par nom et e-mail, la création d'une conversation et un échange avec réponse IA ont été vérifiés depuis le Web. Ces vérifications ne constituent pas une preuve de fonctionnement natif Android ou iOS.

Pour la persistance distante documentée, MongoDB Atlas est fourni au backend via \texttt{MONGO\_URI}. Le code de connexion accepte également une base MongoDB locale ou une base en mémoire pour le développement et les tests ; ces variantes ne doivent pas être confondues avec Atlas. La vérification effectuée dans ce rapport porte sur l'API publique et le parcours Web ; les paramètres privés de la base distante ne sont pas exposés.

Les alternatives du sujet (Vue.js, Flutter, Firebase, Auth0, Kafka, LangChain) \textbf{n'ont pas été mises en œuvre}.

\subsection{Temps réel}

Lors d'une connexion Socket.io, le client peut \texttt{join\_conversation} ou \texttt{leave\_conversation}. Le backend émet \texttt{message\_received} et \texttt{conversation\_updated} vers la salle. Les événements globaux \texttt{conversation\_created} et \texttt{conversation\_updated} servent au rafraîchissement des listes.

\subsection{Statistiques}

\texttt{getStats} calcule le nombre total de conversations, les résolutions par IA ou par un humain, la moyenne des notes renseignées et un \textbf{temps de réponse moyen} à partir des messages.

\subsection{Téléversement}

Multer enregistre les fichiers avec un nom unique. Types acceptés : images, vidéos, PDF et Word. La taille maximale est configurable (\texttt{MAX\_UPLOAD\_SIZE\_MB}, défaut 15~Mo) et le type MIME déclaré est filtré.

\section{Moteur IA}

Le fichier \texttt{geminiService.js} enchaîne : retrieval $\rightarrow$ construction du prompt $\rightarrow$ essai de modèles Gemini $\rightarrow$ repli RAG textuel. La FAQ d'exemple couvre notamment : suivi de commande, retard, remboursement, mot de passe, code promo. Elle n'est pas un corpus métier confidentiel de SINAPS TEC.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.38\textheight,keepaspectratio]{images/Pipeline RAG de SINAPS.png}
\caption{Pipeline de recherche augmentée par génération (RAG) de SINAPS}
\label{fig:rag-pipeline}
\end{figure}

Le retriever normalise le français (minuscules, accents, apostrophes et ponctuation), tokenise les textes, retire des mots vides et applique une normalisation de variations lexicales. Il calcule ensuite des vecteurs TF-IDF et plusieurs similarités cosinus : question (poids 0,5), mots-clés (0,3), texte combiné (0,1) et réponse (0,05), avec un bonus pour les mots-clés pertinents. Seuls les documents dont le score est strictement supérieur à \textbf{0,35} sont retenus, avec un maximum de \textbf{deux documents} (\texttt{topK = 2}). Les demandes de facturation sont limitées aux documents de catégorie \texttt{billing}. Sans clé Gemini, en cas d'échec du modèle ou sans document pertinent, le service utilise la meilleure réponse locale ou propose une mise en relation humaine.

\section{Frontend}

\subsection{Espace client}

Après identification (\texttt{ClientEntryForm}, bouton Google et/ou formulaire), \texttt{SupportChatApp} charge le fil, affiche \texttt{ChatThread}, \texttt{QuickPrompts}, \texttt{MessageComposer}, et les actions d'escalade / désescalade dans \texttt{ChatHeader}. Un dialogue de satisfaction s'ouvre à la clôture.

Les réponses IA peuvent porter des \textbf{actions rapides} : confirmer que la réponse a suffi, poser une autre question ou demander un agent humain. Une action est envoyée comme message client et son état de chargement est affiché ; les boutons ne sont proposés que sur le dernier message IA éligible. Le compositeur est verrouillé pendant la génération IA afin d'éviter les doublons.

  \subsection{Client mobile}

  Le dossier \texttt{sinaps-mobile/} contient un client Expo / React Native connecté aux mêmes routes HTTP et au même serveur Socket.io que le client web. Il propose l'authentification client par nom / e-mail ou Google, l'authentification agent / administrateur par e-mail et mot de passe, la persistance de session, le chat, les pièces jointes, l'indicateur de frappe, l'escalade, le retour vers l'IA, la clôture avec satisfaction et le mode sombre. Des écrans distincts permettent également à un agent de consulter la file, de prendre en charge une conversation, de répondre et de la résoudre, ainsi qu'à un administrateur de consulter les statistiques, les agents et l'historique.

  Le mobile n'est pas fonctionnellement identique au web : les actions rapides contextuelles attachées à certaines réponses IA sur le web sont remplacées par des suggestions statiques qui envoient directement une question ; son compositeur propose les images et documents, mais pas le parcours vidéo exposé par le web ; et l'inscription d'un agent reste disponible uniquement sur \texttt{/agent/signup}. La connexion Google mobile dépend en outre d'une build native Expo configurée.   Enfin, les valeurs de secours prévues dans l'écran administrateur mobile lorsque les statistiques sont absentes ne doivent pas être considérées comme des mesures de production.   Le client mobile a été lancé en Expo Web sur \texttt{http://localhost:8081} avec l'API Render : l'écran de connexion, l'identification directe, le chargement d'une conversation, l'envoi d'un message, une réponse IA et une connexion Socket.io ont été observés. Cette vérification ne couvre ni une build native Android/iOS ni Google Sign-In natif. Le dépôt contient la configuration TypeScript du client mobile, mais aucune suite de tests automatisés mobile n'est présente.

  \section{Données de démonstration}

Le script \texttt{npm run seed} recrée des comptes d'exemple (mot de passe de seed : \texttt{password123}) : administrateur \texttt{admin@sinaps.com}, agents validés et un agent en attente, plus des utilisateurs et conversations de démonstration. Ces comptes servent aux captures et aux tests manuels ; ils ne constituent pas une population réelle de production.

\section{Mise en route (développement local)}

\begin{lstlisting}[caption={Démarrage local (d'après le README du projet)},label=lst:run]
# MongoDB Atlas : renseigner MONGO_URI
cd sinaps-backend && npm install && npm run seed && npm run dev
cd sinaps-project && npm install && npm run dev
\end{lstlisting}

Variables nécessaires côté backend : \texttt{PORT}, \texttt{MONGO\_URI}, \texttt{JWT\_SECRET}, \texttt{GEMINI\_API\_KEY}, \texttt{GOOGLE\_CLIENT\_ID} ; côté frontend : \texttt{NEXT\_PUBLIC\_API\_URL}, \texttt{NEXT\_PUBLIC\_GOOGLE\_CLIENT\_ID}. Sans clés Google/Gemini, des modes dégradés existent (identification directe, réponses RAG locales). Le dépôt confirme l'intégration de Google Sign-In, Gemini et MongoDB Atlas, mais ne fournit pas de compte rendu détaillé d'une recette manuelle en conditions réelles.
