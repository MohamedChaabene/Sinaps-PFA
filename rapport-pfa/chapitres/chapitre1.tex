\subsection{Contexte fonctionnel et projet Op Support IA}

Une demande de support typique (suivi de commande, retard, remboursement, mot de passe, code promotionnel) traverse plusieurs étapes : qualification, recherche d'information, réponse, éventuellement transfert vers un humain, puis clôture et recueil d'avis. Sans outil dédié, ces étapes se perdent dans la messagerie personnelle ou un standard téléphonique. Les conséquences habituelles sont :

\begin{itemize}[leftmargin=1.4em]
  \item une charge répétitive pour les opérateurs sur des questions déjà documentées ;
  \item l'absence de \textbf{traçabilité} (statut, interlocuteur, pièces jointes, historique) ;
  \item l'impossibilité de distinguer ce qui a été résolu par une FAQ de ce qui a nécessité un humain ;
  \item un faible pilotage (délai de première réponse, satisfaction).
\end{itemize}

Le projet, intitulé dans le cahier des charges \textit{Projet de stage --- Support by IA} / \textit{Op Support IA}, consiste à concevoir une application de support dans laquelle :

\begin{enumerate}[leftmargin=1.6em]
  \item le client émet une demande dans une interface de chat ;
  \item un \textbf{agent IA} interroge une base de connaissances (RAG) et répond ;
  \item un \textbf{workflow} suit la demande (prise en charge IA, attente d'un humain, résolution) ;
  \item le client peut \textbf{basculer} vers un opérateur humain ;
  \item l'échange peut inclure des pièces jointes ;
  \item la clôture s'accompagne d'une \textbf{note de satisfaction} ;
  \item l'administrateur valide les agents et consulte statistiques et historique.
\end{enumerate}

Le produit livré comprend une application \textbf{web} (interface responsive) et un client mobile \textbf{Expo / React Native} connecté au même backend. Le mobile couvre l'authentification, le chat, les réponses IA, l'escalade humaine, la clôture avec satisfaction, les pièces jointes, le temps réel Socket.io, ainsi que des écrans agent et administrateur. Il ne constitue toutefois pas une copie fonctionnellement identique du web : l'interface mobile propose des actions rapides contextuelles attachées aux réponses IA éligibles, avec une présentation adaptée aux petits écrans et différente de celle du web. La connexion Google mobile nécessite une build native Expo configurée. Aucune recette formelle de cette version n'est documentée.

\section{Problématique}

Une FAQ seule suffit pour les cas les plus fréquents mais :

\begin{itemize}[leftmargin=1.4em]
  \item elle n'entretient pas un fil de discussion ;
  \item elle ne déclenche pas d'escalade ni d'assignation ;
  \item elle n'enregistre ni SLA ni note de satisfaction.
\end{itemize}

À l'inverse, un chat 100~\% humain (ou un e-mail) offre la souplesse d'un opérateur, mais chaque message consomme du temps humain, y compris pour les demandes déjà couvertes par la connaissance métier. Le sujet cherche donc un \textbf{compromis} : l'IA en première ligne, l'humain sur demande ou lorsque la base ne suffit pas.

Le sujet du stage pose ainsi la question d'ingénierie logicielle suivante : \textbf{comment automatiser une partie du support tout en conservant une bascule humaine fluide et une supervision administrative ?}

\section{Objectifs}

À partir du cahier des charges et des choix techniques retenus avec l'encadrant (React / Next.js, Express, MongoDB, Gemini, JWT), les objectifs opérationnels ont été :

\begin{itemize}[leftmargin=1.4em]
  \item disposer d'un chat client francophone, authentifié (Google ou identification par nom et e-mail) ;
  \item répondre automatiquement via RAG + Gemini, avec un repli local si l'API générative est indisponible ;
  \item permettre l'escalade et le retour vers l'IA, l'affectation d'un agent, et la clôture notée ;
  \item offrir un espace agent (file, réponses, pièces jointes) et un espace admin (validation, SLA, historique) ;
  \item persister les données sur MongoDB et documenter l'utilisation de MongoDB Atlas pour l'environnement distant, puis diffuser les mises à jour par WebSocket (Socket.io) ;
  \item documenter et tester le backend (santé API, autorisations, upload, retriever).
\end{itemize}

\section{Méthodologie et démarche}

Le stage n'a pas suivi un cadre Scrum (pas de sprints planifiés, pas de daily, pas de tableau Kanban documenté). Le travail s'est organisé de manière \textbf{itérative et informelle} : lecture du sujet, choix d'architecture, implémentation fullstack, sécurisation des routes, ajout des tests, puis rédaction du présent rapport.

Les outils utilisés en plus du code source sont : \textbf{Visual Studio Code}, \textbf{Cursor}, \textbf{Antigravity}, \textbf{GitHub}, ainsi que les consoles \textbf{Google} (OAuth, Gemini) et \textbf{MongoDB Atlas}. Postman est mentionné dans la documentation du projet pour les vérifications manuelles de l'API ; aucun compte rendu détaillé ni collection Postman n'est conservé dans le dépôt.
