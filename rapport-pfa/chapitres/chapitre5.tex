\chapter{Tests et validation}

\section{Introduction}

Cette phase vise à vérifier que les principaux comportements du backend de SINAPS correspondent aux besoins retenus : authentification, conversations, messages, traitement IA, prise en charge humaine, administration et téléversement. Les résultats présentés sont fondés sur les tests présents dans le dépôt et sur l'exécution de la suite backend. Aucun pourcentage de couverture, aucun temps de réponse mesuré en production et aucun recettage utilisateur formalisé n'est avancé.

\section{Stratégie de test}

La stratégie combine plusieurs niveaux de vérification réellement présents dans le projet :

\begin{itemize}[leftmargin=1.4em]
  \item des tests automatisés backend, exécutés avec Jest ;
  \item des tests d'intégration HTTP avec Supertest, utilisant MongoDB Memory Server pour isoler les données ;
  \item des tests unitaires ciblés, notamment pour le middleware d'authentification, le formatage des horodatages et le retriever RAG ;
  \item des tests du téléversement avec Multer, des actions rapides, du cycle de résolution et du filtrage des données de démonstration ;
  \item Postman est mentionné dans la documentation du projet pour les vérifications manuelles de l'API ; aucun compte rendu détaillé ni collection Postman n'est conservé dans le dépôt.
\end{itemize}

Le frontend Next.js et l'application mobile ne contiennent pas de suite de tests automatisés dédiée dans le dépôt. Une validation manuelle des interfaces est possible, mais ses dates, scénarios détaillés et résultats ne sont pas documentés de manière vérifiable dans les sources disponibles.

La suite backend est lancée avec la commande suivante :

\begin{lstlisting}[caption={Exécution de la suite backend}]
cd sinaps-backend
npm test
\end{lstlisting}

\subsection{Authentification, conversations et messages}

\texttt{auth-middleware.test.js} couvre l'absence de header, les jetons invalides, les rôles inadaptés et l'appartenance à une conversation pour \texttt{requireClientAuth}, \texttt{requireConversationAccess} et \texttt{requireSenderAuth}. Les tests du flux agent vérifient l'escalade, l'assignation, la réponse humaine, la résolution, la protection contre la prise d'une conversation déjà attribuée et le scénario complet IA $\rightarrow$ humain $\rightarrow$ résolution.

Les tests d'actions rapides vérifient notamment leur stockage, leurs identifiants, leur idempotence, la mise à jour de \texttt{lastActivityAt} et les actions de confirmation, de nouvelle question et d'escalade. Les tests d'horodatage contrôlent la présence et la sérialisation de \texttt{createdAt} lors du chargement d'une conversation agent.

\subsection{Upload et retriever RAG}

\texttt{upload.test.js} vérifie le refus d'une requête sans session, le refus d'un type interdit, l'acceptation d'un fichier JPEG côté client et d'un PDF côté agent, la limite de taille fixée par le test à 1~Mo et la sécurisation de l'extension d'un sous-type image atypique.

\texttt{rag.test.js} contrôle que des formulations liées au suivi de commande ou au remboursement récupèrent l'entrée correspondante, qu'une requête sans rapport ne retourne aucun document et qu'une question de facturation n'est pas dirigée vers une réponse de suivi de commande. Le repli de \texttt{getAIResponse} sans clé Gemini est également vérifié. Ces tests valident le retriever local et le repli ; ils ne mesurent pas la qualité linguistique de Gemini en production.

\subsection{Résultat de la suite}

La dernière exécution locale de la commande \texttt{npm test} a produit le résultat suivant :

\begin{center}
\textbf{13 suites passées, 205 tests passés, 0 échec, 0 snapshot}
\end{center}

Cette exécution couvre le backend. Elle ne constitue ni une mesure de couverture ni une garantie de performance en production.

\section{Résultats et anomalies corrigées}

Les tests dédiés documentent plusieurs problèmes rencontrés puis corrigés pendant le développement :

\begin{itemize}[leftmargin=1.4em]
  \item \textbf{État de prise en charge IA :} les conversations nouvellement créées devaient conserver \texttt{handledBy = ia} afin de déclencher correctement la réponse IA. Les tests couvrent aussi le comportement par défaut des conversations héritées sans valeur explicite.
  \item \textbf{Persistance et chargement des messages :} le traitement attend la création du message IA avant de répondre à la requête HTTP, et le rechargement d'une conversation retourne les messages persistés avec leurs horodatages.
  \item \textbf{Réponses de facturation :} une question concernant une facture ne doit pas recevoir par erreur la réponse relative au suivi d'une commande ; le retriever et le repli sont testés sur ce cas.
  \item \textbf{Authentification des messages humains :} un message \texttt{sender = humain} exige une session agent ou administrateur, tandis qu'un client ne peut envoyer qu'un message dans sa propre conversation.
  \item \textbf{Escalade et assignation :} les tests vérifient la séparation entre prise en charge IA et humaine, l'assignation à un agent et la prévention d'un changement silencieux d'agent.
  \item \textbf{Données de démonstration :} les conversations marquées \texttt{isTestData} sont exclues des listes administratives par défaut afin de ne pas fausser les indicateurs opérationnels.
\end{itemize}

\section{Validation finale}

La version évaluée dispose d'une suite backend reproductible qui couvre les principaux flux d'API, la persistance MongoDB en mémoire, l'authentification, les conversations, le RAG local, les réponses de repli, les pièces jointes, les actions rapides, les horodatages et l'administration. L'exécution confirmée aboutit à 205 tests réussis répartis sur 13 suites.

Les limites restantes sont les suivantes :

\begin{itemize}[leftmargin=1.4em]
  \item aucun test E2E de navigateur avec Playwright ou Cypress n'est présent dans le dépôt ;
  \item aucun test de charge Socket.io n'est présent ;
  \item aucune recette formelle signée par l'encadrant n'est documentée ;
  \item les indicateurs du tableau de bord dépendent des données effectivement présentes ; le jeu de démonstration est marqué \texttt{isTestData} et exclu par défaut ;
  \item aucune preuve de déploiement public ni mesure de production n'est fournie dans le dépôt ;
  \item les tests automatisés ne permettent pas de conclure à une validation complète des interfaces Web et Mobile.
\end{itemize}

\section{Conclusion}

Les tests backend automatisés ont permis de vérifier les principaux comportements fonctionnels et plusieurs corrections importantes de SINAPS. Les résultats obtenus sont reproductibles et couvrent les flux essentiels de l'API, tout en laissant clairement identifiées les limites liées aux tests d'interface, de charge et de validation en production.
