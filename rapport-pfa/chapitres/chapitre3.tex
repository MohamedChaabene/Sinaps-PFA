\chapter{Conception du système}

Ce chapitre traduit les besoins du chapitre~2 en vues d'architecture, de données et de comportement. Les diagrammes correspondent au \textbf{système implémenté}, pas à la stack maximale listée dans le document de sujet (Python, PostgreSQL, React Native, Kafka, etc.).

\section{Architecture générale}

Le système est une architecture \textbf{à deux applications} communiquant par HTTP(S) et WebSocket, avec une base documentaire MongoDB.

Les flux principaux sont :

\begin{enumerate}[leftmargin=1.6em]
  \item le navigateur charge l'UI Next.js (routes App Router) ;
  \item les appels métier passent par \texttt{/api/...} sur Express ;
  \item après un message client, si la conversation est en mode IA, le backend appelle le retriever puis Gemini (ou le repli) et enregistre un message \texttt{ia} ;
  \item Socket.io notifie la salle \texttt{conversation\_<id>} et, pour les listes, un événement global ;
  \item les fichiers sont stockés sur disque sous \texttt{uploads/} et servis en statique.
\end{enumerate}

Cette vue correspond à la figure \og Clients / Frontend / Backend / Agent IA / Base / Admin \fg{} du sujet, avec des choix figés : \textbf{pas} de React Native, \textbf{pas} de Python, \textbf{MongoDB} (et non PostgreSQL), \textbf{Gemini} (et non OpenAI / LangChain).

\section{Description des cas d'utilisation principaux}

\subsection{CU01 --- S'identifier (client)}

Le client fournit un \textbf{jeton Google} (vérifié avec \texttt{GOOGLE\_CLIENT\_ID}) ou un couple nom / e-mail. Le serveur trouve ou crée un \texttt{User} et délivre un JWT de rôle \texttt{client} (durée 30~jours). Une conversation non résolue est réutilisée, sinon une nouvelle conversation est créée (\texttt{handledBy = ia}, \texttt{status = en\_cours}).

\subsection{CU02 --- Envoyer un message}

Précondition : session client et conversation ouverte. Le message est persisté. Si \texttt{handledBy = ia}, le service IA produit une réponse enregistrée comme message \texttt{ia}. Les deux messages sont émis sur Socket.io.

\subsection{CU03 --- Escalader}

Le client (ou un profil autorisé sur la conversation) passe \texttt{handledBy} à \texttt{humain} et \texttt{status} à \texttt{en\_attente}. Les agents voient le fil dans la file.

\subsection{CU04 --- Traiter une demande (agent)}

L'agent authentifié (compte \texttt{approved}) consulte la liste, peut être assigné (\texttt{assignedAgent}, statut \texttt{en\_cours}), répond avec \texttt{sender = humain}, puis clôture.

\subsection{CU05 --- Administrer}

L'admin consulte \texttt{GET /api/stats} et \texttt{GET /api/conversations}, approuve (\texttt{status = approved}) ou supprime un agent en attente.

\subsection{Escalade vers un humain}

Le client appelle \texttt{PATCH /conversations/:id/escalate}. Le document passe à \texttt{handledBy = humain}, \texttt{status = en\_attente}. Socket.io émet \texttt{conversation\_updated} vers la salle et en global, afin que l'espace agent rafraîchisse la file.

\subsection{Clôture et satisfaction}

\texttt{PATCH /conversations/:id/close} accepte une note entière entre 1 et 5. Une valeur hors intervalle (par exemple 0) \textbf{n'est pas} enregistrée comme satisfaction, afin d'éviter de fausser la moyenne. Le statut devient \texttt{resolu}.

\section{Conception de l'authentification et des droits}

Deux familles de jetons JWT signés avec \texttt{JWT\_SECRET} coexistent.

\begin{table}[H]
\centering
\caption{Politique d'authentification}
\label{tab:auth}
\small
\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
Profil & Mécanisme \\
\midrule
Client & JWT \texttt{role=client}, 30~jours, après Google (ID token vérifié) ou find-or-create e-mail. Stockage navigateur : \texttt{sinaps\_client}. \\
Agent / admin & JWT \texttt{role=agent$\mid$admin}, 7~jours, après e-mail + mot de passe. Refus si agent \texttt{pending}. Stockage : \texttt{sinaps\_token}. \\
Middleware & \texttt{requireAuth}, \texttt{requireAdmin}, \texttt{requireAgentOrAdmin}, \texttt{requireClientAuth}, \texttt{requireConversationAccess}, \texttt{requireSenderAuth}, \texttt{requireAnySession}. \\
\bottomrule
\end{tabularx}
\end{table}

Règles importantes :

\begin{itemize}[leftmargin=1.4em]
  \item un client ne lit et ne modifie que \textbf{sa} conversation ;
  \item \texttt{sender = humain} exige un JWT agent/admin ;
  \item \texttt{sender = ia} est refusé s'il vient d'une requête externe (création interne seulement) ;
  \item l'upload exige une session client ou agent (pas d'anonyme).
\end{itemize}

En production, le serveur \textbf{refuse de démarrer} sans \texttt{JWT\_SECRET}. En développement, une clé de test est utilisée avec un avertissement.

\section{Conception du moteur RAG et de l'escalade}

\subsection{Retriever}

La base \texttt{data/knowledgeBase.js} contient un tableau \texttt{\{ question, answer \}}. Chaque document est tokenisé (minuscules, suppression de mots vides français), indexé en TF, pondéré par IDF, puis comparé à la requête par \textbf{similarité cosinus}. Les extraits dont le score dépasse $0{,}05$ sont retenus (\texttt{topK = 2} pour le prompt).

Ce n'est \textbf{pas} un RAG vectoriel (pas d'embeddings, pas de base vectorielle). C'est un RAG \og lexical \fg{} suffisant pour une petite FAQ de démonstration.

\subsection{Génération}

Si une clé Gemini valide est présente, un prompt français injecte les extraits \og Savoir pertinent \fg{} et demande une réponse courte, avec consigne d'orienter vers le bouton d'escalade si l'action sur compte est manuelle. Plusieurs noms de modèles sont essayés en cascade (\texttt{gemini-3.5-flash}, \texttt{gemini-3.6-flash}, \texttt{gemini-flash-latest}). En échec, le premier extrait RAG ou un message d'invitation humaine est renvoyé.

\subsection{Escalade}

L'escalade n'est \textbf{pas automatique} selon un score de confiance. Elle est \textbf{décidée par l'utilisateur} (ou un acteur autorisé sur la conversation) via l'API. C'est un choix volontaire du MVP, cohérent avec le bouton \og Basculer vers un agent humain \fg{} du sujet.
